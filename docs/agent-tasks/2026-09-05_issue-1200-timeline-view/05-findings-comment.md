### Findings for #1200 — answers against the ADRs (2026-09-05)

**Sources checked:** `ORISO-Docs/oriso-platform/decisions/ADR-001…018`, `ORISO-Frontend/CONTEXT.md` (Activity Timeline glossary), `ORISO-Docs/product/*`, and the code on `dev` @ `ad5c8c21`. **No ADR answers any of the three questions.** ADR-012 only sequences the timeline integration, ADR-018 only requires an exception to the filter that drops system notifications, ADR-004/005 give the E2EE boundary. The Activity Timeline ADRs **ADR-AT-01/02/03** that `CONTEXT.md`, `timelineFilter.ts` and `ConversationPreview.tsx` cite live in "OrisoPlan WP-06" and are **not in ORISO-Docs**. The referenced "notification-center analysis" is, as far as we can find, `ORISO-Docs/oriso-platform/dsfa-analysis/dsfa-deepdive-notification-center.md` (DSFA deep-dive 3, dated **2026-08-14**, on `dev`) — @Storypapst please correct if a different 2026-08-01 document was meant. It confirms the mechanics below: `PATCH /users/event-notifications/read-all` (§1.4), preview mode fixed to `NONE` so no chat content ever reaches `event_notification` (§1.3), and `read_date` as a per-notification timestamp it recommends reducing to a flag (§3c). Because nothing authoritative exists, the answers below cite `CONTEXT.md` + code, and I drafted **ADR-019** in ORISO-Docs (PR linked below) so they get a citable home pending product sign-off.

**JOB1 — checkmark (✓✓, tooltip "Mark all as read").** It is the bulk read action for **activity events**: `PATCH /service/users/event-notifications/read-all` (UserService), then every loaded card gets `readAt` and the unread counter drops to 0 (`NotificationsProvider.markAllNotificationsAsRead`). It sets `read_date` on the user's own `event_notification` rows (self-scoped, DSFA §1.4) and does **not** send Matrix read receipts or change chat badges/session state — the Activity Timeline is not the Matrix room timeline (`CONTEXT.md` "Timeline collision"; `event_notification` is append-only with `markAsRead` as its only mutation). The tooltip is accurate. Divergence found: the button was always enabled, so with nothing unread it was a silent no-op → **fixed: disabled while nothing is unread** (PR below). If the overloaded word "notification" confuses, the remedy is copy ("Mark all activity as read") — a product call, not a behaviour change.

**JOB2 — status of the chat shown inside the detail pane.** The pane has two modes ("Show details" / "Show conversation preview"). _Details_ shows the selected event's icon, client-rendered title/text, timestamp ("waiting since …" for waiting-room events, #845) and handover consent actions. _Preview_ is `ConversationPreview` (#847): a **read-only** render of the last 50 messages of the linked room from the app's own Matrix client (ADR-AT-01: previews are hydrated client-side, never server-side). It **never registers an active view and never sends read receipts**, so viewing it changes no status anywhere — it replaced an iframe that booted a second SPA and suppressed the very `message.new` events the timeline shows. So the status you see is _the activity event's own state_ (type, read/unread, time) plus _a snapshot of the room as your client sees it_; acting on the conversation goes through the event's red action-target button. No divergence; documented in ADR-019 §2.

**JOB3 — where is the extended filter bar?** It is the bar in the screenshot. Filter chips are **data-driven**: one chip per event family present in the loaded feed, canonical order requests → messages → drafts → handover → calls → system → appointments (`timelineFilter.ts` `getFamiliesInFeed`), plus the orthogonal **Unread** toggle and the client-side search. A dedicated "Alle" chip was removed on design feedback 2026-07-12 (no selection = everything). A feed containing only request events therefore shows exactly "Requests · Unread · ✓✓". Divergence found: `CONTEXT.md` still said "'Alle' shows everything" → **corrected** in the PR; nothing to restore or remove in the UI.
